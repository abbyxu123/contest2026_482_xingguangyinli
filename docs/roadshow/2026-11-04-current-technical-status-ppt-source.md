## 3. 产品到底是什么

### 推荐定义

> **画间是一幅运行 openvela 的家庭共享 AI 画框：它能感知有人到来、允许家庭成员通过
> 角色配件表达意愿，再通过语音或触控完成一次受约束的晚餐协商。**

它不是普通智能屏，也不是自动点餐机。核心区别在于：

- 手机擅长个人搜索与支付，画间负责共享空间里的共同表达；
- AI 负责理解和生成候选，确定性代码负责复核、确认和退出；
- 物理触点让家庭成员不必每次拿出手机或打开 App；
- 系统把最终决定和付款留给人。

### 当前主场景

“今天晚饭吃什么？”是第一条可完整验证的产品链：

1. presence 让画框知道“有人到来”，但不知道“是谁”。
2. 猫 A/B 让系统知道“哪位家庭成员表达了意愿”。
3. 语音或触控补充预算、辣度、忌口、人数、是否做饭等真实约束。
4. AI 返回少量、结构化的候选和理由。
5. 本地规则再次校验预算、过敏、动作和链接边界。
6. 用户明确二次确认后，画框才出现手机接续。
7. 手机完成平台搜索、最终选择和付款；画框不持有支付权限。

## 4. 当前系统架构

### PPT 架构图建议

```text
匿名毫米波 presence ─┐
猫 A / 猫 B 触摸签到 ─┼─> Gemini S1 / openvela
麦克风与画框触控 ─────┘          │
                                  ├─ LVGL 中文界面与产品状态机
                                  ├─ 本地约束、权限与失败降级
                                  ├─ ai_agent / Dinner Assistant Skill
                                  └─ 受限 API ─> ASR / 推荐模型 / TTS
                                                   │
                                                   └─ 手机接续，不代付款
```

### 角色分工

| 组件 | 当前职责 | 明确不负责 |
| --- | --- | --- |
| Gemini S1 / openvela | 唯一产品状态、UI、确认、触控、语音、配件编排 | 不保存支付账号，不让模型直接控制危险动作 |
| 本地/边缘后端 | ASR、结构化推荐、TTS、鉴权、会话、记忆和配件中继 | 不拥有最终确认权，不伪造真机状态 |
| 猫 A/B ESP32 | 独立角色身份、触摸表达、签名事件和明确反馈 | 不是主控，不复制完整画框产品，不直接访问公网后台 |
| 毫米波 | 匿名有人/无人事件 | 不做人脸、身份、情绪或健康识别 |
| 手机 | 确认后的平台搜索和付款 | 不承担家庭共享空间的前置协商 |

### 架构上的关键判断

- 一个主 Agent，而不是五个拥有权限的自治 Agent；角色只提供受限表达。
- 端侧负责状态、确认和降级；云侧负责自然语言与候选生成。
- 配件可以离线或失败，但不能拖垮主画框的基本流程。
- 正式网络和现场私网备用必须显式区分，不做不可见的自动降级。

## 6. AI 与 Dinner Assistant Skill 目前到什么程度

### 已实现的 AI 边界

- 自定义 `Dinner Assistant Runtime Contract` 已进入公开仓库。
- Skill 规定最多返回少量候选，必须说明事实来源和不确定性。
- 模型输出不是直接设备命令，而是受限结构化数据。
- 本地代码复核预算、过敏/忌口、辣度、做饭意愿、URL 和动作白名单。
- 模型不能直接写长期记忆、下单、付款或控制任意硬件。
- 临时偏好只属于当前会话；长期偏好必须由用户明确保存，并支持查看、纠正和删除。
- 没有足够真实偏好时，应继续询问或规则降级，不能假装“已理解用户”。

### 已有证据

- Skill 文件、元数据和运行时合同测试通过。
- 后端结构化推荐、拒绝、确认、会话原子性和记忆边界已有测试。
- 主机端曾完成真实模型会话，包括候选、角色贡献、显式确认和手机接续。

### 仍需真机证明

- S1 上的 ai_agent 能发现并加载当前 Skill。
- 真实板载语音输入调用 Skill，并把结果正确显示和播报。

### 推荐 PPT 结论

## 10. 双猫角色配件目前到什么程度

### 产品意义

两只猫不是两块缩小版主屏，而是两个家庭成员的低门槛表达入口：

- 猫 A 与猫 B 使用同一套公开代码，但身份、密钥、会话和反馈彼此独立；
- 用户轻触自己的猫，表达“我到家了”或“我也有意见”；
- 画框首次接受事件后记录角色并返回签名 ACK；
- 猫验证身份、会话、序号和 HMAC 后才显示“画框回应了”。

### `PASS-SW`

- 独立 A/B 身份和独立 256 位密钥；
- 随机启动会话、递增序号、会话内防重放；
- HMAC-SHA256 完整性验证；
- 最多三次有限重试；
- duplicate ACK 不重复触发 UI 或家庭事件；
- 错误身份、错序号、篡改包和伪造 ACK 被拒绝；
- 单台失败不应阻塞另一台或主画框；
- 猫咪 UI、触摸边沿、发送中/成功/失败状态明确；
- 真正的 Arduino ESP32-S3 工具链已构建联网版本，而非只做 Mock。

### 2026-11-04 新增

- 主/备用双网络自动轮换；
- 网络与本地画框端点成对切换；
- 断线重建 UDP 状态；
- 离线稳定渲染，减少全屏闪烁；
- A/B 三方私密配对包和安全交付工具。

### `PENDING-HW`

- 最新固件尚需在两台实体猫上逐台核对身份、备份、刷写和写后校验；
- 需要各自完成真实主网络、备用热点和签名 ACK；
- 需要证明 A/B 不串台、单台离线不影响另一台。

### PPT 可用结论

> 双猫证明的是“一个 openvela 主控可以安全编排多个有角色身份的家庭触点”，而不是简单增加
> 两个遥控器。

## 12. 安全、隐私与可靠性是怎么做的

### 数据最小化

- 无摄像头，不采人脸。
- 毫米波只输出 presence，不做生命体征或身份推断。
- 语音由明确交互启动，不做持续监听。
- 音频在结束、取消或错误后擦除。
- 真实 Wi-Fi、密钥、设备身份、备份和 token 不进入公开仓库。

### AI 权限最小化

- AI 只返回候选和理由。
- 本地规则复核硬约束和动作白名单。
- 用户未确认时不能出现手机接续。
- 画框不保存支付账户，不执行付款。

### 多设备可信

- 每只猫独立 ID 与密钥；
- 消息包含启动会话与递增序号；
- HMAC 验证来源和完整性；
- 重复包可确认但不重复记事件；
- 当前防重放重点是同一启动会话内，不能夸大为跨所有重启的永久防重放。

### 工程恢复

- 设备刷写前核对 USB 身份、芯片身份和目标角色；
- 保留备份、哈希和恢复工具；
- 公开软件门禁不接触真实秘密和硬件写入；
- 增强项失败时保留已验证的触控/二维码底线。

## 15. 项目的技术难点不只是“接了几个传感器”

### 难点 1｜RTOS 主控上的完整产品状态

画间需要同时处理 UI、触控、语音、AI 请求、配件事件、presence 和失败恢复。真正的难度
是保持唯一状态所有者，避免迟到响应、重复事件或配件离线把界面带入错误状态。

### 难点 2｜模型能力与设备权限分离

模型给出自然语言候选，但硬约束、确认、记忆和手机接续由确定性代码控制。这样既保留 AI
能力，又避免模型直接操作设备或支付。

### 难点 3｜一主多配件的可信协作

双猫不是匿名广播按钮，而是独立身份、密钥、会话、序号、重试和 ACK 的配件协议；新增
双网络容错后，还需要保证网络切换不削弱身份与签名边界。

### 难点 4｜真实世界的失败恢复

项目显式处理断网、模型失败、ASR 超时、迟到任务、配件离线、重复包、错误刷写和现场网络
变化。演示不是只证明“成功一次”，而是证明失败时不会伪造结果或破坏底线。

## 16. 产品创新可以怎么讲

### 三种互补输入

1. **presence** 回答“有人来了吗”。
2. **角色配件** 回答“谁表达了意愿”。
3. **自然语言** 回答“具体想要什么”。

它们不是重复传感器，而是补齐家庭协商的三个不同信息层。

### 从个人终端到共享空间

手机是个人设备，画间是共享空间入口。它允许家庭成员以轻触、在场和简短语音参与同一
决策，而不是让一个人替所有人操作手机。

### 克制的 AI

画间不追求“AI 自动替你做完一切”，而是把候选、解释、确认和退出做清楚。对家庭场景，
可信和可恢复比无边界自动化更重要。

### 艺术与技术融合

画框仍然是作品主体；屏幕、角色、触摸和灯光只在需要时出现。产品目标不是把平板装进
相框，而是让实体绘画成为环境式交互界面。

## 17. 商业化可以怎样“微微画饼”而不失真

### 最小产品形态

**主画框 + 角色配件 + 可选 AI 服务**

- 主画框：openvela 主控、显示、音频、匿名 presence 和本地状态机。
- 角色配件：同一固件平台，不同身份/外壳/角色，可一只起步、多人扩展。
- AI 服务：基础规则与本地交互可继续工作，模型增强按需要启用。

### 可验证的商业假设

- 主画框承担平台价值，角色配件承担个性化与家庭成员扩展。
- 用户可能为艺术外观、家庭角色和持续 Skill 扩展付费，而不是只为一块屏幕付费。
- 先验证持续使用、成功率和单位会话成本，再讨论规模化定价。

### 推荐的 50 户四周试点

- 每户每周主动发起次数；
- 从发起到候选的中位时间与失败率；
- 确认、拒绝、修改比例；
- 实体触点、语音和触屏的使用占比；
- 断网成功率和恢复时间；
- 用户对 presence、录音和记忆边界的理解度；
- 单次 AI 会话成本。

### 不能提前宣称

- 不能写已有销售、量产、渠道合同或真实毛利。
- 不能把旧 BP 价格假设当作市场验证。
- 不能把计划中的 50 户试点写成已经完成。
